2.1 Diagrama de Contexto del Sistema (C4 Nivel 1)

Explicación y Justificación Arquitectónica del Contexto

El diagrama de contexto ilustra la interacción de los tres actores principales con la plataforma StyleRadar y sus integraciones externas: 1. Usuario Comprador: accede desde aplicaciones Web/Móvil para explorar el catálogo y enviar solicitudes de ajuste de prendas en su propio cuerpo mediante la subida de una fotografía frontal. 2. Tienda Aliada: administra prendas y activa la disponibilidad de modelos para prueba virtual. 3. Administrador: supervisa cuotas globales y audita el cumplimiento de políticas de privacidad. La frontera del sistema alberga el orquestador PT8080-VirtualTryOn-Service (puerto 8092), el cual se comunica hacia el exterior con: a) FASHN AI VTON SaaS: clúster externo de GPUs sobre Kubernetes que ejecuta difusión generativa profunda para transferir la prenda sobre la silueta del usuario mediante HTTPS TLS 1.3. b) Azure Blob Storage: almacén seguro donde las fotos de los usuarios se resguardan temporalmente con URIs firmadas (SAS Tokens de 15 minutos) y eliminación física irreversible. c) RabbitMQ: broker de eventos para comunicar el fin del renderizado hacia servicios como notificaciones y recomendaciones sin bloqueos HTTP sincrónicos.

·
Regla de Oro Aplicada: Justificación de Fronteras Se seleccionó una integración asíncrona desacoplada hacia el SaaS FASHN AI para aislar al sistema StyleRadar de la latencia inherente del procesamiento de redes neuronales (15-28s), evitando la saturación de hilos del servidor web local y garantizando alta disponibilidad.

2.2 Diagrama de Componentes General (C4 Nivel 2 / Contenedores y Servicios)

Explicación y Justificación de las Conexiones entre Componentes

La arquitectura de contenedores garantiza desacoplamiento absoluto y alta escalabilidad: 1. Entrada Única (API Gateway - Puerto 8080): Las aplicaciones clientes interactúan únicamente con Spring Cloud Gateway. El Gateway intercepta las solicitudes, valida el token JWT RS256 contra Redis, aplica Rate Limiting (Token Bucket) y redirige de forma transparente hacia los microservicios internos. 2. Enrutamiento hacia PT8080 (Puerto 8092): Las solicitudes bajo la ruta /api/v1/probador/** son despachadas hacia ms-probador-virtual. Este microservicio ejecuta la validación de cuotas del usuario en su base de datos local probador_db y gestiona el ciclo de vida del job. 3. Comunicación Asíncrona (RabbitMQ): Para evitar el acoplamiento temporal entre servicios, cuando un render de probador virtual culmina con éxito, ms-probador-virtual emite el evento tryon.job.completed hacia el exchange styleradar.exchange. Dicho evento es consumido de forma reactiva por ms-notificaciones (para enviar alerta push al cliente) y ms-recomendaciones (para alimentar el motor de sugerencias basadas en estilo). 4. Database-per-Service: Cada microservicio es dueño absoluto de su esquema de persistencia. ms-probador-virtual no comparte tablas con ningún otro microservicio; mantiene su PostgreSQL 16 para persistencia transaccional y Redis 7 para estados volátiles de jobs.

·
Regla de Oro Aplicada: Protocolos de Comunicación La comunicación externa utiliza HTTPS/REST con OpenAPI 3.0 para estandarización y consumo ágil desde interfaces web; la comunicación interna entre microservicios se rige por eventos AMQP 0-9-1 a través de RabbitMQ para garantizar tolerancia a fallos.

2.3 Diagrama de Despliegue (Contenedores, Puertos y Redes)

Explicación y Justificación de la Topología de Despliegue

La topología de despliegue define la infraestructura de contenedores OCI tanto para el entorno de desarrollo local (Docker Compose) como para el despliegue en la nube (Azure Container Apps / Kubernetes): 1. Red Aislada (styleradar-net): Red virtual tipo bridge con direccionamiento privado 172.28.0.0/16 que interconecta todos los contenedores sin exponer puertos de base de datos a redes públicas. 2. Contenedor de Aplicación (sr-probador-virtual): Construido a partir de Eclipse Temurin 17 JRE sobre Alpine Linux (imagen ultra-ligera < 180MB). Expone el puerto 8092 mapeado al host. Cuenta con configuración de memoria JVM acotada (-XX:MaxRAMPercentage=75.0) y reinicio automático (restart: unless-stopped). 3. Almacenamiento y Caching Dedicados: • sr-probador-postgres: PostgreSQL 16 Alpine en puerto local 5442 (mapeado a 5432 del contenedor) con volumen persistente vton_postgres_data montado en /var/lib/postgresql/data. • sr-probador-redis: Redis 7 Alpine en puerto local 6389 (mapeado a 6379 interno) con persistencia RDB activada sobre el volumen vton_redis_data. 4. Broker Central (sr-rabbitmq): RabbitMQ 3.13 con plugin de gestión habilitado (puerto 5672 para protocolo AMQP y puerto 15672 para consola web administrativa).

·
Regla de Oro Aplicada: Paridad Desarrollo-Producción La orquestación mediante Docker Compose garantiza paridad exacta entre el ambiente de pruebas local de los desarrolladores y el pipeline de integración continua CI/CD en GitHub Actions, ejecutando los mismos contenedores y healthchecks.

Requerimientos No Funcionales (RNF) y Privacidad Biométrica

RNF-SEC-01 / SR-RNF-02: Habeas Data Biométrico

En cumplimiento estricto de la Ley 1581 de 2012 de Colombia y normativas GDPR de protección de datos personales, las fotografías frontales de los usuarios son consideradas datos biométricos sensibles. El servicio implementa: 1) Encriptación AES-256 en reposo y TLS 1.3 en tránsito. 2) Borrado Físico Irreversible: Purga automática de la foto original a los 15 minutos de completado el render. 3) Derecho al Olvido: Endpoint dedicado DELETE /api/v1/probador/fotos/{id} para purga inmediata.

RNF-LAT-01 & RNF-DISP-01: Rendimiento y Resiliencia

1) Latencia de Orquestación: Respuesta de aceptación de jobs en menos de 300 ms gracias al procesamiento no bloqueante con Spring WebFlux. 2) Tolerancia a Fallos: Implementación de patrón Circuit Breaker con Resilience4j. Si la API de FASHN AI no responde o agota créditos, el sistema conmuta automáticamente al MockVirtualTryOnAdapter sin provocar fallas en cascada ni caídas del servicio.

ARQUITECTURA HEXAGONAL ESPECÍFICA

Estructura estricta de Puertos y Adaptadores del microservicio PT8080-VirtualTryOn-Service, garantizando independencia total del framework respecto a la lógica de negocio.

Diagrama de Componentes Específico (Puertos y Adaptadores)

Explicación y Justificación de la Arquitectura Hexagonal

La arquitectura hexagonal organiza el código en tres capas concéntricas con regla de dependencia hacia adentro: 1. Adaptadores de Entrada (Driving / Primarios): VirtualTryOnRestController expone los endpoints REST bajo el estándar OpenAPI 3.0, transformando las peticiones HTTP/JSON en DTOs inmutables de aplicación. RabbitTryOnListener recibe comandos asíncronos desde colas AMQP. 2. Puertos de Entrada (Input Ports): Interfaces Java puras (ProcesarTryOnUseCase, ConsultarEstadoTryOnUseCase, ConsultarCuotasUseCase) que declaran los contratos de las operaciones del caso de uso. 3. Capa de Aplicación: Clases de servicio como ProcesarTryOnServiceImpl orquestan la ejecución: validan la existencia de cuota mensual, invocan la carga de la imagen y despachan el procesamiento sin acoplarse a librerías de infraestructura. 4. Dominio Puro (Core): Contiene las entidades TryOnJob, UserTryOnQuota y Value Objects. No contiene ninguna anotación de Spring, JPA, Hibernate o JSON; es código Java 17 puro testeable al 100% en milisegundos. 5. Puertos de Salida (Output Ports): Interfaces (TryOnRepositoryPort, VirtualTryOnAiPort, PhotoStoragePort, TryOnEventPublisherPort) mediante las cuales la aplicación solicita servicios externos. 6. Adaptadores de Salida (Driven / Secundarios): Implementaciones concretas como PostgreSqlTryOnRepositoryAdapter (Spring Data JPA), RedisTryOnCacheAdapter, RabbitMqEventPublisherAdapter y el Dual Adapter de IA (MockVirtualTryOnAdapter para pruebas a costo $0 y FashnAiAdapter para el SaaS real).

·
Regla de Oro Aplicada: Inversión de Dependencias El núcleo de negocio nunca depende de la base de datos ni del proveedor de IA. Si en el futuro se reemplaza FASHN AI por Google Imagen 3 o una red VTON on-premise, únicamente se escribe un nuevo adaptador de salida sin modificar una sola línea del dominio.

MODELO DE DOMINIO Y DIAGRAMA DE CLASES

Diseño guiado por el dominio (Domain-Driven Design): agregados, entidades, value objects inmutables e invariantes de negocio del microservicio de probador virtual.

Diagrama de Clases del Dominio (DDD)

Explicación y Justificación del Modelo de Dominio

El modelo de dominio implementa patrones tácticos de DDD para encapsular la lógica de negocio y proteger sus invariantes: 1. Aggregate Root (TryOnJob): Entidad raíz que controla el ciclo de vida completo de una solicitud de prueba virtual. Encapsula las transiciones de estado permitidas a través de una máquina de estados determinista (PENDING → PROCESSING → COMPLETED / FAILED). Ningún cliente externo puede modificar el estado directamente sin invocar los métodos de negocio iniciarProcesamiento(), completar() o fallar(). 2. Entidad UserTryOnQuota: Gestiona la cuota mensual de pruebas asignada al usuario comprador. Implementa la regla de negocio que limita a 10 pruebas gratuitas por mes calendario. Su método consumirCuota() lanza la excepción de dominio QuotaExceededException si el límite ha sido alcanzado, garantizando que el sistema no realice consumos innecesarios de la API de IA. 3. Value Objects Inmutables: • FrontalPhoto: Valida la URL de acceso temporal, verifica que el formato sea estrictamente compatible (JPEG, PNG) y calcula el checksum SHA-256 para evitar reprocesar imágenes idénticas. • GarmentReference: Identifica la prenda a probar y valida que su categoría sea soportada por los modelos de difusión de ropa (ej. tops, vestidos, pantalones). • TryOnResult: Representa el resultado inmutable de la inferencia neuronal, conteniendo la URL de la imagen generada, el tiempo de procesamiento en milisegundos y el índice de confianza. • JobStatus: Enumeración estricta que define los estados válidos de un trabajo.

·
Regla de Oro Aplicada: Dominio Puro y Libre de Frameworks Todas las clases de este diagrama se implementan como POJOs y Java Records inmutables en el paquete domain.model sin ninguna anotación de Hibernate (@Entity), Spring o Jackson, garantizando portabilidad absoluta y tests unitarios ultrarrápidos.

MODELO DE BASE DE DATOS ESPECÍFICO

Esquema físico relacional de la base de datos probador_db en PostgreSQL 16: definición de tablas, claves primarias/foráneas, índices optimizados y reglas de integridad.

Diagrama de Base de Datos (Modelo Entidad-Relación Físico)

Explicación y Justificación del Esquema Físico

El esquema físico de persistencia en PostgreSQL 16 está diseñado bajo principios de normalización relacional, integridad ACID y rendimiento en consultas concurrentes: 1. Tabla try_on_jobs: Almacena el historial transaccional de pruebas virtuales. Utiliza identificadores universales únicos (UUID) como clave primaria generados por el cliente o la aplicación para evitar contención de secuencias en clústeres distribuidos. Cuenta con un índice B-Tree compuesto sobre (user_id, status) para acelerar la consulta del dashboard del usuario, y un índice sobre created_at para soportar los jobs periódicos de purga física de fotografías según Habeas Data. 2. Tabla user_try_on_quotas: Mantiene el saldo de pruebas mensuales del usuario. Posee una restricción de unicidad (UNIQUE) sobre la columna user_id para garantizar una sola fila por usuario en cada período de facturación. La actualización de cuota utiliza transacciones con bloqueo pesimista (SELECT ... FOR UPDATE) para prevenir condiciones de carrera cuando un usuario dispara múltiples clics simultáneos. 3. Tabla try_on_audit_logs: Registro de auditoría inmutable en modo append-only. Guarda cada acción sobre el sistema (creación de job, cambio de estado, solicitud de eliminación biométrica) con marca temporal TIMESTAMPTZ y detalles contextuales en formato JSONB para cumplimiento legal y forense.

·
Regla de Oro Aplicada: Justificación del Motor de Persistencia Se seleccionó PostgreSQL 16 por su robustez en transacciones ACID para las cuotas de usuario, soporte de tipos nativos UUID y JSONB para auditoría, y perfecta compatibilidad con Flyway para migraciones de esquema versionadas en el pipeline de CI/CD.
